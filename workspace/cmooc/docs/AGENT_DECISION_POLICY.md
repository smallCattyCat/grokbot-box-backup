# 代理决策规则：默认推进，边界才询问

- 更新日期：`2026-07-31`
- 状态：`CURRENT DEVELOPMENT POLICY`

## 用途

这是一张按需查阅的决策表，不是新的审批流程。日常工作遵循一个问题：

> 下一步是否会跨越用户拥有的外部、不可逆或科研证据边界？

如果不会，直接做；如果会，只隔离并询问那一个动作，同时继续其余安全工作。

开发选择还要先过一个结果门：

> 它是否直接推进 `PRODUCT_CURRENT.md` 的当前纵向切片、成熟产品的自主闭环、
> 可观测可靠性、主要研究问题的证据，或解除一个已经复现的真实阻塞？

若均不是，不新建抽象、客户端、adapter、角色、审批层或技术报告。产品能力不必
为了取得“研究阶段”名称而等待新的论文证据；安全修复和可靠性工作也可独立完成，
但都应服务当前产品闭环。

完成判定必须区分代码存在、本地验证、真实只读路径、真实外部运行和教育效果。已有
schema、API、页面或单元测试但生产调用为 0 时，继续推进合流，不写成已完成；反之，
较新的自治/Graph 实现也不得为了迁就旧阶段文档而回退。

## Proceed / Ask

| 情形 | 默认动作 | 说明 |
| --- | --- | --- |
| 仓库内、任务范围内、可回滚的代码或文档修改 | **Proceed** | 采用现有模式，实施后跑针对性验证 |
| 命名、文件布局、小型实现取舍存在歧义 | **Proceed** | 选择最小方案；只记录影响结果的假设 |
| 读取代码、公开文档或公开开源案例 | **Proceed** | 公共检索词中不得包含论坛正文、私有键或研究行 |
| 只读审计 `01_原始数据` 或正式匿名数据 | **Proceed** | 不覆盖、不改名、不原地生成产物；结果进入隔离研究目录 |
| 构建 mock、fixture、dry-run、影子模式和本地测试 | **Proceed** | 可证明协议复现或实施保真，不得冒充真实论坛行为或教育效果 |
| 在已绑定测试课程上用 API、Chrome、Computer Use 或 Playwright 观察、导航、展开、滚动和核验 | **Proceed** | 每次核验 origin、courseId、页面身份和动作后置条件；不绕过平台权限 |
| 在测试课程编辑器中写入草稿、回读并清空，但不提交 | **Proceed** | 属于 STAGE 传输验证；禁止点击发布、提交快捷键和真实通知 |
| 建设持久调度、事件账本、课程图、世界状态、恢复机制和定时任务入口 | **Proceed** | 它们是自主产品主线，不再按“未来基础设施”后置；默认 OBSERVE/SHADOW |
| 在硬锁下实现发布、幂等、重试、核对和恢复代码 | **Proceed** | 开发完整执行能力与激活真实外部效果是两件事；保持 `realPublishEnabled=false` |
| 安装当前纵向切片直接需要的普通开发依赖 | **Proceed** | 先确认已有依赖不能满足；锁版本并验证，不为猜测安装 |
| 向在线模型或外部服务发送论坛研究内容 | **Ask** | 需要用户对当前任务的明确授权；授权不能沿用到以后 |
| 没有有效 `AutonomyPolicy` 时执行真实发布或通知 | **Ask** | 只阻塞该次外部动作；观察、影子决策、草稿和执行能力开发继续 |
| 在有效 `AutonomyPolicy` 与当前明确授权范围内执行真实动作 | **Proceed** | 策略必须绑定课程、动作、预算、有效期、停机条件和幂等核验；一次性授权、STAGE 与 Permit 消费后不能沿用 |
| 删除或覆盖原始/正式数据、共享库或用户改动 | **Ask** | 先精确解析目标，并优先提供可恢复方案 |
| 缺少凭据、账户权限或外部所有者决定 | **Ask** | 只询问不可替代的权限，同时完成本地部分 |
| 互斥选择会改变研究问题、标签含义、时间窗或数据契约 | **Ask** | 先给出现有证据和最小两个选项，避免开放式讨论 |

## 永不绕过

- 不通过改写命令、换工具或间接调用绕过一次被拒绝的授权。
- 不关闭未来信息泄漏检查、发布门禁、目标/正文绑定、幂等或远端结果核验来换取
  “流程跑通”。
- 不将课程身份解释为知识等级或固定促进者身份。
- 不把相关性、回放表现或人工一致性写成已经发生的干预因果效应。
- 不读取、输出或提交完成任务并不需要的密钥、Cookie、密码和认证状态。
- 不把 2026-07-31 的一次 L3 成功、已消费 Permit 或 pending outcome 窗解释为后续
  真实发布授权。

## 授权门前的继续策略

1. 把需要授权的最小动作写清楚，例如“发送这 60 条匿名正文到在线模型”或
   “对这一个已审阅目标执行真实发布”。
2. 完成不依赖该动作的观察、影子决策、接口、执行器、恢复、测试、审计与文档。
3. 验证授权门确实 fail closed，并留下可恢复状态。
4. 最后只向用户请求那项具体授权，不把整个阶段标成阻塞。

## 验证与 Git 成本分层

| 改动范围 | 最低验证 |
| --- | --- |
| `AGENTS.md` 或本规则 | `npm run verify:agent-guidance`；`git diff --check` |
| 单模块 TypeScript | 直接相关测试；`npm run type-check`；`npm run lint` |
| 决策快照、scheduler、研究契约 | `npm run test:research`；对应 audit/status；未来后缀不变性检查 |
| 状态机、发布内核、跨模块协议 | 相关单元/集成测试；`npm run verify` |
| 生产构建路径实际改变 | 上述相关检查；`npm run build` |

输入没有变化时不重复同一检查。与当前改动无关的既有失败单独报告，不伪装成新
失败，也不自动阻止完成本次可验证成果。任务被称为“阶段检查点”本身不是重复
全量验证或运行 build 的理由。

一个明确的开发检查点至多创建一个聚焦提交。分析、评审、无实质改动或不能与
用户工作干净隔离时，不为满足流程制造提交。需要提交时先检查完整 diff 和 staged
敏感文件。

## 防止流程膨胀

- 不为假设性风险增加新智能体、审批层、委员会式角色或通用抽象。
- `ObservedEventLedger`、Course Event World、连续调度、Decision Tape、结果观察
  和浏览器/API 双通道是当前自主产品的必要组成，不应再被“防止扩建”规则误判为
  流程膨胀。是否建设由当前纵向切片和验收条件决定，而不是等待新的逐项审查。
- 第二客户端、MCP 或通用工具协议只在真实第二消费者出现后建设；新平台抽象至少
  需要两个当前消费者，或一个已复现的不兼容问题。
- 优先把稳定不变量写成代码测试；只有出现可复现的机械违规，才考虑 hook。
- 不默认添加项目 `.codex/config.toml`、hooks 或 `.rules`。若同一个安全命令在至少
  三个独立任务中反复触发同类审批，再基于实际记录提出一个窄前缀规则；不要允许
  `powershell`、`python`、`node` 或 `npm` 这类宽前缀。
- 规则本身若不再服务当前主线，应删除或收窄，而不是继续叠加例外。
- 仅当入口、当前状态或操作方法改变时，更新既有 README 或当前工作流；不为内部
  切片新建阶段报告。
